| 6 | AB测试数据 | `/api/dual-rating/ab-test` | GET | 中 |
| 7 | 评分对话列表 | `/api/dual-rating/conversations-by-rating` | GET | 高（含脱敏） |

**请确认**：
- [ ] 所有接口路径和方法无异议
- [ ] 接口复杂度评估是否准确
- [ ] 是否有其他技术限制

## 二、数据脱敏要求（重点）

### 2.1 需脱敏的敏感信息类型

| 标签 | 类型 | 示例 |
|------|------|------|
| `[P:n]` | 人名 | 张三 → [P:1] |
| `[C:n]` | 公司/机构名 | 阿里巴巴 → [C:1] |
| `[S:n]` | 学校名 | 北京大学 → [S:1] |
| `[H:n]` | 医院名 | 协和医院 → [H:1] |
| `[O:n]` | 其他组织 | XX社区 → [O:1] |
| `[L:n]` | 地点/地址 | 朝阳区XX路 → [L:1] |
| `[T:n]` | 电话号码 | 138xxxx → [T:1] |
| `[D:n]` | 身份证号 | 110xxx → [D:1] |
| `[N:n]` | 其他证件号 | 护照号 → [N:1] |
| `[M:n]` | 金额/财务 | 50万 → [M:1] |

### 2.2 脱敏处理流程

```
原始对话 → NER识别 → 实体映射 → 人工审核 → 脱敏文本
```

**请确认**：
- [ ] 是否有现成的 NER 服务可用
- [ ] 人工审核环节如何实现（需产品确认流程）
- [ ] 脱敏处理是实时还是异步

## 三、数据库设计要求

### 3.1 核心表结构

需要设计的表：

1. **conversations** - 对话元数据表
2. **raw_messages** - 原始消息表（敏感，需权限控制）
3. **masked_messages** - 脱敏消息表（对外提供）
4. **entity_mapping** - 实体映射表（用于溯源）

### 3.2 数据存储策略

- 原文与脱敏文本**双轨存储**
- 实体映射关系需保留，支持溯源
- 敏感数据访问需记录日志

**请确认**：
- [ ] 是否使用现有数据库，还是新建
- [ ] 数据库类型（MySQL/PostgreSQL/其他）
- [ ] 是否需要数据访问审计日志

## 八、产品已确认事项

| 问题 | 决策 | 说明 |
|------|------|------|
| 脱敏处理时机 | **异步处理** | 对话结束后异步脱敏，不影响查询性能 |
| 历史数据处理 | **需要处理** | 历史数据量约 **1万条以内**，需全量脱敏 |
| 缓存策略 | **需要缓存** | 统计类数据 **每小时更新** 一次 |

### 8.1 脱敏处理实现要求

- 对话结束后触发异步脱敏任务
- 脱敏完成前，对话内容接口返回"处理中"状态
- 建议使用消息队列（如 RabbitMQ/Redis）管理脱敏任务

### 8.2 历史数据迁移要求

- 历史对话数据量：约 1 万条
- 需要一次性批量脱敏处理
- 建议编写迁移脚本，分批执行
- 迁移完成后需人工抽检确认

### 8.3 缓存实现要求

- 缓存对象：用户评分统计、AI评估统计、AB测试数据
- 缓存更新频率：每小时
- 建议使用 Redis 作为缓存层
- 缓存 Key 设计建议：`dual-rating:{type}:{date}`
